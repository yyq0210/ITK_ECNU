# ITK 医学影像库鲲鹏平台移植与混合精度优化 — 项目报告

**项目名称：** ITK 5.4 在华为鲲鹏（ARM64）高性能计算平台上的移植、性能评估与混合精度优化  
**报告日期：** 2026 年 6 月  
**测试平台：** 华东师范大学 HPC 环境（`202.120.87.20`，96 逻辑核鲲鹏服务器）  
**本地工作区：** `D:\ECNU_HPC\ITK_huawei`  
**ITK 版本：** Insight Toolkit（ITK）5.4.0  

---

## 摘要

本项目将开源医学影像处理库 **ITK 5.4** 部署到 **华为鲲鹏 ARM64 服务器**上，完成了从环境搭建、编译移植、多核并行性能评估，到 **混合精度（float/double）优化** 的完整工作链路。

主要成果包括：

1. **成功在鲲鹏平台编译并运行 ITK**，解决了路径迁移、工具链版本、汇编器与 `-march=native` 冲突等问题，并启用 **ARM NEON 向量化**编译选项。  
2. **建立可复现的性能测试体系**（绑核、线程扫频、多算子 benchmark），摸清不同算子在 96 核上的加速规律。  
3. **完成混合精度优化方案设计与实测**：应用层 float 化在滤波环节可达 **1.2–2.1 倍**加速且精度无损；配准环节 **约 1.36 倍**加速；对 ITK 源码的针对性补丁对卷积类算子额外带来 **约 1–7%** 收益。  
4. **产出完整文档、脚本与 benchmark 程序**，可供后续课题与生产 pipeline 直接引用。

**一句话：** 本项目不是从零写一套影像软件，而是把业界标准的 **ITK** 可靠地跑在 **国产鲲鹏 CPU** 上，并系统性地做了 **「跑得对、跑得快、省内存」** 三方面工作。

## 第一部分：项目背景（给非技术读者）

### 1.1 什么是 ITK？

**ITK（Insight Toolkit）** 是国际主流的 **医学图像处理 C++ 库**，由 NumFOCUS 基金会维护，广泛用于：

- MRI / CT 等影像的 **滤波、分割、配准（对齐）**  
- 科研与工业中的 **图像分析 pipeline**

可以把它理解为医学影像领域的「标准工具箱」——很多论文和软件底层都在用 ITK，而不是每个课题组自己重写滤波、配准算法。

### 1.2 为什么要做「移植」？

**移植**在这里的意思是：让原本多在 **x86（Intel/AMD）** 服务器上开发和测试的 ITK，在 **华为鲲鹏（ARM64）** 机器上也能 **正确编译、正确运行、发挥多核性能**。

动机包括：

| 动机 | 说明 |
|------|------|
| **国产化算力** | 鲲鹏等 ARM 服务器在高校、云、政企中 increasingly 常见，需要验证主流科研软件能否用好 |
| **性能摸底** | 96 核服务器上，ITK 到底能加速多少？是否「核越多越好」？需要实测而非猜测 |
| **内存与精度** | 医学影像体积大，**降低单像素精度（float 替代 double）** 可减半内存、提升带宽利用率，但需保证结果仍可用于诊断或科研 |

### 1.3 什么是「混合精度」？

计算机里浮点数常见两种宽度：

| 类型 | 约占用 | 精度 | 典型用途 |
|------|--------|------|----------|
| **float（单精度）** | 4 字节/像素 | 较低，但对很多影像足够 | 滤波、分割中间结果 |
| **double（双精度）** | 8 字节/像素 | 较高 | 配准优化、几何变换、多步迭代 |

**混合精度** = 在 pipeline 不同阶段 ** deliberately 选用不同精度**：例如图像用 float 存，配准时变换参数仍用 double 算——既省内存又保证关键步骤数值稳定。

这与 AI 训练里的 FP16/BF16 混合精度 **概念类似**，但 ITK 没有 PyTorch 那种全局自动框架，需要 **按模块、按算子** 设计和验证。

### 1.4 本项目的工作边界

| 做了 | 没做（或列为后续） |
|------|-------------------|
| ITK 5.4 鲲鹏 CPU 编译与运行 | ITK GPU / CUDA / OpenCL 模块（鲲鹏节点无 NVIDIA GPU） |
| 单机 96 线程 + 双机 MPI  smoke 测试 | 大规模生产级 MPI 体数据 pipeline |
| 混合精度方案 + 多算子 benchmark | BF16 像素类型、ITK 全库 NumericTraits 改造 |
| 源码级 float 累加补丁（实验性） | 向 ITK 上游提交 patch（当前为本地维护脚本） |

### 3.2 鲲鹏 SIMD 与编译器标志适配（关键移植难点）

**问题 1：** 系统脚本 `kunpeng-simd.sh` 会注入 **`-O3 -march=native`**。GCC 10 据此生成 **`armv8.2-a+crypto+dotprod+fp16fml`** 等指令，但系统 **汇编器 as 2.27 过旧**，无法识别 `dotprod` 等扩展 → **编译在探测阶段即失败**。

**问题 2：** 若完全不用向量选项，ITK 能编过，但 **无法利用 NEON**，性能损失大。

**处理（已写入 `build-yyq` 配置）：**

- 配置/编译时使用 **`env -i` 洁净环境**，避免继承 `-march=native`  
- 显式设置 **`-O3 -march=armv8.2-a+crypto`**：在旧 `as` 能力范围内启用 **ASIMD/NEON**  
- **禁止** 在当前节点使用 `-march=native`

**验证：** 对测试代码 `objdump` 可见 **`fmla v*.4s`**（float 向量乘加），证明向量化生效。

**意义：** 这是在鲲鹏上「**能编过且跑得快**」的核心工程决策，属于典型 **移植调优**，而非 ITK 业务逻辑修改。

---

### 3.3 多核并行与 CPU 绑核

**背景：** ITK 5.4 默认用 **线程池（Pool）** 做 Filter 内并行，**不是** OpenMP。仅设置 `OMP_NUM_THREADS` **不能**控制 ITK 线程数。

**建立的使用规范：**

| 环境变量 / 手段 | 作用 |
|----------------|------|
| `ITK_GLOBAL_DEFAULT_NUMBER_OF_THREADS=96` | 设置 ITK 线程数 |
| `ITK_GLOBAL_DEFAULT_THREADER=Pool` | 指定线程后端 |
| `taskset -c 0-95` | 将进程绑定到 0–95 号 CPU，便于公平对比与 `htop` 观察 |

**性能摸底结论（对非技术读者最重要）：**

|  workload 类型 | 多核行为 |
|--------------|----------|
| **小图 / 轻量算子**（如 256² 滤波） | 16 核附近即「见顶」，96 核无明显收益 |
| **大图 Bilateral**（1024²～16384²） | 线程越多收益越大；16384² 上 96 核相对单核约 **28 倍** |
| **迭代扩散 CAD/GAD** | **16 核左右最优**，96 核反而更慢（同步与依赖开销） |

**意义：** 避免「盲目开满 96 线程」；为后续混合精度测试提供了 **统一的性能基线**。

## 第四部分：优化工作（混合精度与性能）

移植解决「**能跑**」；优化解决「**跑得好、省资源**」。

### 4.1 总体策略

```
┌─────────────────────────────────────────────────────────┐
│  读入影像（推荐 Image<float>，4 字节/像素）              │
├─────────────────────────────────────────────────────────┤
│  滤波 / 分割：float 算子（RecursiveGaussian、Otsu 等）   │
│  可选：ITK 源码补丁（卷积类额外 ~1–7%）                  │
├─────────────────────────────────────────────────────────┤
│  配准：float 存图 + double 变换/度量/优化器（官方推荐模式）│
├─────────────────────────────────────────────────────────┤
│  写回结果                                                │
└─────────────────────────────────────────────────────────┘
```

**明确放弃：** 「float → cast 到 double → 计算 → cast 回 float」的 **hybrid 链**——实测 **比全程 double 更慢**。

---

### 4.2 应用层优化（不改 ITK 源码，**推荐默认**）

只需在应用程序里使用 **`Image<float>`** 及 ITK 官方已支持 float 的 Filter。

| 模块 / 算子 | 相对 double 存储路径 | 精度（vs double） |
|-------------|---------------------|-------------------|
| **RecursiveGaussian 平滑** | **1.2–2.1×**（2D 真实 MRI） | 完全一致（max_abs=0） |
| **Median + Gaussian 链** | **1.36–1.44×** | 完全一致 |
| **DiscreteGaussian** | **1.24–1.30×** | 完全一致 |
| **Otsu 分割** | **1.21–1.33×** | 完全一致 |
| **Metricsv4 配准** | **~1.36×**（273 ms vs 371 ms） | 平移误差 < 0.003 mm |

**机理（通俗）：** float 图像 **占内存减半**，CPU 读写的数据量变小，缓存更友好；RecursiveGaussian 等算子 ITK 内部 **本来就用 float 做中间计算**，所以加速明显。

---

### 4.3 源码补丁（深入 ITK 内部，实验性）

#### 补丁是什么？

**补丁** = 用脚本修改 **ITK 安装目录里的 C++ 头文件**（不是改我们的 demo），改完后 **必须重新编译 ITK**。

**为什么要补丁？**  
许多 Filter 即使用 `Image<float>`，内部仍 typedef 成 **`RealType = double`**，CPU 实际执行 **double 指令**，算力省不下来。补丁把关键 typedef 改成 **`FloatType`（float）**。

#### 三批补丁

| 批次 | 修改对象 | 影响算子 | 实测额外加速 |
|------|----------|----------|--------------|
| **补丁 1** | Bilateral、Mean、DiscreteGaussian 头文件 | 邻域累加改 float | 卷积类 **~2–4%** |
| **补丁 2** | Bilateral 核、查表、内层循环 | 全路径 float | 相对补丁 1 **几乎无额外收益** |
| **补丁 3** | 有限差分基类、Box 工具函数 | CAD、GAD、BoxMean | BoxMean **~2%**；CAD **~3.5%** 但误差增大 |

补丁脚本：`2026-0507/itk_float_accum_patches/`（含 `apply_*.sh` 与 `revert_*.sh`）。

**结论：** 补丁是 **锦上添花**；**主收益来自应用层 float 化**。大图 Bilateral 仍受 **内存带宽** 限制，不宜期望 float 带来 2 倍算力。

---

### 4.4 性能测试与 benchmark 程序

为让结论 **可复现、可写进论文/报告**，编写了专用测试程序：

| 程序 | 测试内容 |
|------|----------|
| `precision_pipeline_bench` | 滤波 / 分割 pipeline（float vs double） |
| `precision_conv_bench` | Bilateral、Mean、DiscreteGaussian、BoxMean、FFT 卷积 |
| `precision_bilateral_bench` | Bilateral 专项（含大图） |
| `precision_registration_bench` | Metricsv4 配准 float 存储 vs double 存储 |
| `precision_diffusion_bench` | CAD / GAD 扩散滤波 |

配套一键脚本（Windows `.cmd` + Linux `.sh`）可在远端自动：**打补丁 → 重编 ITK → 跑 benchmark → 写日志**。

---

### 4.5 重要发现（可向老师强调的「科研价值」）

1. **「用了 float 图像」≠「内部用 float 算」**——ITK 默认行为导致许多算子仍 double 计算；需源码审计 + 反汇编验证。  
2. **加速比 strongly 依赖算子与数据规模**——同一台 96 核机器，RecursiveGaussian 小图 ~2×，大图 Bilateral 补丁后仍 ~1%。  
3. **混合精度必须分算子验收**——CAD 50 次迭代后 float/double 差异可达 **~20 灰度级**；GAD 则几乎无损。  
4. **配准适合「float 存 + double 算」**——与 ITK 官方 Example 一致，实测 **更快且收敛一致**。

## 第七部分：结论与建议

### 7.1 项目结论

1. **移植目标已达成：** ITK 5.4 在华为鲲鹏 96 核服务器上 **稳定编译运行**，NEON 向量化与多线程性能已系统评估。  
2. **优化目标部分达成：** 应用层混合精度 **显著** 降低内存并提升滤波/配准性能；源码补丁对重卷积算子 **增量有限** 但完成了机理验证。  
3. **方法论可复用：** 「审计 → 扫频选型 → float 化 → 补丁 → benchmark 验收」可推广到其他 Filter 或 ITK 版本。

### 7.2 生产 / 课题建议

| 建议 | 说明 |
|------|------|
| 滤波、分割默认 **Image<float>** | 简单、收益大、精度已验证 |
| 配准采用 **float 图像 + double 度量/优化器** | 与 ITK 官方一致 |
| 线程数 **按算子调** | Bilateral 大图可用 64–96 核；扩散迭代类建议 16–32 核 |
| 源码补丁 **按需启用** | 维护成本随 ITK 升级而增加 |
| CAD 等迭代算子 **慎用补丁 3** | 需视觉或指标级验收 |

### 7.3 后续工作

1. 端到端业务 pipeline benchmark（非单算子）  
2. MPI 体数据分块 + float 计算的规模化测试  
3. `ITK_USE_FLOAT_SPACE_PRECISION` 等编译选项实测  
4. CAD 补丁精度验收或回退 double 内部  
5. BF16 / 上游 patch 贡献（远期）
