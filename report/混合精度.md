# ITK 混合精度优化方案

**版本：** 2026-06-10（修订）  
**适用环境：** ITK 5.4.0，x86 96 逻辑核（`202.120.87.20`）  
**相关实测：** [`操作记录_ITK混合精度真实数据测试_2026-05-31.md`](./操作记录_ITK混合精度真实数据测试_2026-05-31.md)、[`操作记录_ITK绑核更大Example扫频_2026-05-17.md`](./操作记录_ITK绑核更大Example扫频_2026-05-17.md)

## 1. 前提：ITK 中的「混合精度」指什么

ITK **没有** PyTorch / CUDA 那种「同一算子自动 FP16/BF16 + loss scaling」的全局混合精度框架。在 ITK 语境下，混合精度通常指：

1. **按模板参数选择像素类型**——存储用 `float`，关键步骤用 `double`（或反之）。
2. **用 `itk::CastImageFilter` 在 pipeline 中切换精度**——仅在确有精度/性能需求时使用。
3. **Filter 内部**——中间变量用 `NumericTraits<TPixel>::RealType`（多为 `double`），输出写回 `TPixel`。

本仓库示例工程 `itk_hybrid_precision_demo` / `mpi_hybrid_precision_demo` 即采用第 2 种做法。

## 2. ITK 现有的精度相关基础设施

### 2.1 `SpacePrecisionType`（`itkFloatTypes.h`）

```cpp
#if defined(ITK_USE_FLOAT_SPACE_PRECISION)
using SpacePrecisionType = float;
#else
using SpacePrecisionType = double;
#endif
```

- 编译选项 `ITK_USE_FLOAT_SPACE_PRECISION` 仅将 **origin / spacing / direction** 等空间元数据从 `double` 降为 `float`。
- **不影响**像素计算、Filter 内部累加、配准度量。
- 可作为编译选项顺手开启，但**不应期望**由此带来 pipeline 级别的显著加速。

### 2.2 `NumericTraits` 的精度分层

每个像素类型的 `NumericTraits` 特化定义了：

| 类型别名 | 典型含义 |
|---------|---------|
| `FloatType` | 较低精度浮点（多为 `float`） |
| `RealType` | 较高精度浮点（多为 `double`） |
| `AccumulateType` | 累加用类型（多为 `double`） |

这些是 **编译期固定** 的，不能运行时切换。

**重要限制：** 并非所有 Filter 都通过 `NumericTraits::FloatType` 做内部计算。许多实现直接硬编码 `double` 或使用 `TPixel` 本身。因此，**仅修改 `NumericTraits` 不会让全库自动变成混合精度**——每个热点 Filter 需单独审计与改造。

### 2.3 典型 pipeline 中实际使用的类型

| 场景 | 常见存储类型 |
|------|-------------|
| CT/MRI 原始 IO | `int16` / `uint16` / `short` |
| 滤波 / 分割中间结果 | `float` |
| 配准度量、变换参数 | `double`（刻意高精度） |
| 空间元数据 | `double`（或 `SpacePrecisionType`） |

因此，优化第一步不是「全局 `double→float`」，而是 **审计 pipeline，确认哪些阶段确实在使用 `Image<double>`**。

## 3. 三层优化路径（由易到难）

### 第 1 层：选择性 float 化（应用层，零 ITK 源码修改）

**思路：** 在精度不敏感的阶段使用 `Image<float, Dim>`，配准 / 优化等关键步骤保留 `double`。

**推荐模式（配准场景）：**

```
Image<float> 存储
    ↓
Metric / Optimizer 内部用 double（ITK Metricsv4 默认行为）
    ↓
Transform parameters 保持 double
```

**不推荐的模式（cast 链 hybrid）：**

```
float → Cast→double → Filter → Cast→float   // 两次 cast 开销常大于收益
```

**本仓库实测（`SmoothingRecursiveGaussianImageFilter`，96 线程）：**

| 路线 | 相对 full_double | 说明 |
|------|-----------------|------|
| **full_float** | **1.05–1.73× 更快** | 2D 真实 MRI 约 1.65×；2048² σ=10 约 1.17× |
| **hybrid（cast 链）** | **0.80–0.97×（常慢于 double）** | cast 开销 > double 计算节省 |
| 精度（vs double） | max_abs = 0 | 对该滤波器，float 已足够 |

**结论：**

- 若目标是 **速度** → 滤波 / 分割阶段 **直接用 full_float**，不必 hybrid。
- 若目标是 **精度** → 配准 / 迭代优化 / 多步累积仍建议关键步用 `double`。
- 预期加速 **1.05–1.7×**（取决于算子与数据规模），而非普遍的 1.5–2×。

**适用场景：** 图像滤波、形态学、分割等对逐像素精度不敏感的任务。

---

### 第 2 层：BF16 类型基础设施（ITK fork 级，中期研究）

**思路：** 引入 `bfloat16_t` 像素类型，存储减半，计算时提升到 FP32。

**NumericTraits 特化示例（概念）：**

```cpp
template <>
class NumericTraits<bfloat16_t> {
public:
  using ValueType = bfloat16_t;
  using FloatType = float;        // 计算提升到 float
  using RealType = double;
  using AccumulateType = float;
  // ...
};
```

**工程现实：**

1. 需同步改造：`itkNumericTraits.h`、IO 模块、ObjectFactory、显式模板实例化（`itk*.cxx`）、回归测试。
2. Python Wrapping 几乎不支持自定义 `bfloat16_t`。
3. **CPU 无 AVX512-BF16 时**，BF16 主要省内存带宽，但每次读写需 cast，净收益有限（通常 1.1–1.5×，带宽受限场景）。
4. 完整可用基础设施估计 **≥ 1 个月**，而非「~1 周」。

**BF16 vs FP16：** BF16 指数位与 FP32 相同，动态范围一致，更适合医学影像；FP16 最大值约 65504，易溢出。

---

### 第 3 层：Kernel 级 SIMD 优化（远期，需硬件支撑）

**思路：** 针对计算最密集的操作，在支持 AVX512-BF16 / ARM BF16 的硬件上，实现 BF16 输入 + FP32 累加的 SIMD kernel。

**热点优先级（结合本仓库 2026-05-17 扫频实测重排）：**

| 优先级 | 算子 | 模块 | 理由 |
|--------|------|------|------|
| **P0** | BilateralImageFilter | Filtering | 16384² 单核 ~12 min，96 核 28× 加速，真正重计算 |
| **P1** | 大核卷积 / FFT 卷积 | Filtering/FFT | 内存受限，float 化直接受益 |
| **P2** | 配准 Metricsv4 | Registration | **保留 double 计算**，float 仅作存储 |
| **P3** | 各向异性扩散（CAD/GAD） | AnisotropicSmoothing | 迭代依赖限制并行，96 核反而慢于 16 核 |
| **P4** | SmoothGauss / Resample | Smoothing | 单线程 ~25 ms，降精度几乎无收益 |

**FFT 注意：** FFTW / VNL 仅支持 `float` / `double`。BF16 图像做 FFT 前必须升到 FP32，中间插 BF16 存储层意义有限；**直接用 float 做 FFT 更合理**。

**SIMD 方向（需 AVX512-BF16，概念示意）：**

```cpp
#if defined(__AVX512BF16__)
#include <immintrin.h>
// 使用 __m512bh + _mm512_dpbf16_ps 等专用 intrinsic
// 数据为 16-bit packed 布局，不能用 _mm512_loadu_ps 加载 BF16
#endif
```

## 4. 实施优先级（修订）

| 优先级 | 工作 | 预计收益 | 工作量 | 说明 |
|--------|------|---------|--------|------|
| **P0** | 审计 pipeline，滤波阶段 **full_float** | 1.05–1.7×（算子相关） | 低 | 改模板参数，零 ITK 源码修改 |
| **P0** | 配准保留 **double 度量 / 变换** | 保证收敛 | 低 | float 存储 + double 计算 |
| **P0** | 线程数按 workload 调优 | 最高 28×（Bilateral 大图） | 低 | Bilateral 64–96 核；迭代扩散 16–32 核 |
| **P1** | 开启 `ITK_USE_FLOAT_SPACE_PRECISION` | 元数据微优化 | 极低 | 编译选项，非主路径 |
| **P2** | BF16 类型 + NumericTraits 基础设施 | 后续 kernel 前提 | ≥ 1 月 | ITK fork 级 |
| **P3** | 逐 Filter 改造内部 kernel | 1.1–1.5×（CPU BF16 存储） | 1–2 月/Filter | 需逐 Filter 审计 |
| **P4** | AVX512-BF16 SIMD kernel | 额外算力加速 | 需硬件确认 | 先确认 CPU 是否支持 |

**不建议作为近期主路径：**

- 全局 `Image<double>` → `Image<float>` 无差别替换（许多 pipeline 本就不用 double 存像素）。
- cast 链 hybrid（实测常比 full_float 慢）。
- 指望改 NumericTraits 后全库自动混合精度。

---

## 5. 注意事项

1. **医学影像精度：** CT Hounsfield 约 -1024~3071，`float` 足够；MRI 信号范围更小。但 **配准梯度 / 优化器** 仍需 `double`（或至少 FP32 累加），否则可能不收敛。

2. **多线程：** ITK Filter 默认多线程（TBB / std::thread）。float 存储减半可提升 cache 命中率，但 **线程数需按算子特性选择**——迭代扩散类 96 核可能比 16 核更慢（同步 / 依赖）。

3. **误差验证：** 不能假设 float 与 double 永远等价。对本仓库测试的 RecursiveGaussian + 真实 MRI，差异为 0；配准、Level-set、多步迭代等仍需单独验证。

4. **BF16 on CPU：** 与 GPU Tensor Core 不同，x86 CPU 上 BF16 算力收益 **依赖 AVX512-BF16 或 AMX**；纯软件 BF16↔FP32 转换有开销。

5. **float 为何未带来算力加速（2026-06-10 验证）：** 本机 ITK 已用 **`-march=armv8.2-a+crypto -O3`** 生成 **NEON** 代码；但 `NumericTraits<float>::RealType = double`，多数 Filter（如 Bilateral）邻域运算仍 **double 累加**，反汇编为 **`fmla v*.2d`** 而非 float 4 路。**`Image<float>` 主要省内存，不保证算力翻倍。** 详见 [`操作记录_卷积重算子float_vs_double_2026-06-10.md`](./操作记录_卷积重算子float_vs_double_2026-06-10.md) §8。

6. **Bilateral 补丁 2（2026-06-17）：** 已将域核、值域查表（含 `std::exp` 建表）、内层阈值/索引全部改为 `OutputPixelRealType`（float）。**复测仍仅 ~1% 加速**——`exp` 不在逐像素内层；补丁 1 后乘加已是 float，大图 Bilateral 仍 **内存带宽主导**。详见 [`操作记录_ITK_filter_float累加与配准_2026-06-17.md`](./操作记录_ITK_filter_float累加与配准_2026-06-17.md) §2.5。

## 6. 推荐落地顺序

### 近期（1–2 周）

1. 审计业务 pipeline 中的 `Image<double>` 使用点。
2. 滤波 / 分割改为 `Image<float>`，配准保留 double。
3. 放弃无实测支撑的 cast 链 hybrid。
4. 针对 Bilateral 等重算子，做 float vs double 精度 + 速度对比（与 16384² 扫频对齐）。

### 中期（1–2 月）

1. MPI 体数据分块 + float 计算（参考 `mpi_hybrid_precision_demo`）。
2. 编译 ITK 时开启 `ITK_USE_FLOAT_SPACE_PRECISION`。
3. 按算子特性调线程数（见 [`操作记录_ITK绑核更大Example扫频_2026-05-17.md`](./操作记录_ITK绑核更大Example扫频_2026-05-17.md)）。

### 远期（ITK fork，3–6 月+）

1. ~~确认目标硬件 BF16 指令集支持~~ → 仍待做  
2. ~~Filter 内部 float 累加 POC~~ → **已完成**（Bilateral/Mean/DiscreteGaussian，见 [`操作记录_ITK_filter_float累加与配准_2026-06-17.md`](./操作记录_ITK_filter_float累加与配准_2026-06-17.md)）  
2b. ~~Bilateral 域核/查表/内层 double 路径~~ → **已完成**（补丁 2，仍 ~1% 加速，§2.5）  
3. ~~Metricsv4 float 存储 + double 度量 benchmark~~ → **已完成**（`precision_registration_bench`）  
4. BF16 类型 + NumericTraits 基础设施  
5. 更多 Filter 的 float accum 扩展 / AVX512-BF16 kernel → **TopN 补丁 3 已完成**（CAD/GAD/BoxMean，见 [`操作记录_ITK_topn_filter_float_accum_2026-06-17.md`](./操作记录_ITK_topn_filter_float_accum_2026-06-17.md)）
